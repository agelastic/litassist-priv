Prompt Engineering for LitAssist: OpenAI, Anthropic Claude, Google Gemini, and xAI Grok

LitAssist uses a multi-model pipeline where each command is routed to the model best suited for its task via OpenRouter. The active model inventory includes anthropic/claude-sonnet-4.5, anthropic/claude-opus-4.1, openai/o3-pro, openai/gpt-5.1, openai/gpt-5-pro, google/gemini-2.5-pro, and x-ai/grok-4. This document covers prompt engineering techniques and parameters for each model family, with emphasis on the legal reasoning, verification, and document drafting tasks that LitAssist performs.

OpenAI O-Series Reasoning Models (o3-pro)

The O-series models (o1, o3, o3-pro, o4-mini) are specialised for extended internal reasoning. They operate fundamentally differently from standard GPT models and require a distinct prompting approach:
	*	No System Messages: O-series models do not support system messages. All instructions must go in the user message. LitAssist handles this automatically via the parameter_handler, which detects the model family and moves system content into the user prompt.
	*	No Sampling Parameters: Temperature, top_p, and other sampling controls are not supported. Reasoning depth is controlled exclusively via the reasoning.effort parameter (mapped from LitAssist's thinking_effort config). Higher effort means more internal computation before answering.
	*	Keep Prompts Simple and Direct: OpenAI's February 2025 guidance for reasoning models states: do not say "think step by step," avoid few-shot examples, and avoid over-complicated instructions. The model's internal reasoning process handles decomposition automatically. Adding explicit chain-of-thought instructions is counterproductive -- Wharton research (Swaroop et al. 2025) measured only 2.9-3.1% improvement from CoT prompting on o3-mini and o4-mini, compared with 25-39% improvement on non-reasoning models.
	*	Prefer Clear Task Statements: Rather than prescribing reasoning steps, state the task, the constraints, and the desired output format. For example, LitAssist's draft command sends case facts, a document template, and format requirements to o3-pro without reasoning scaffolding -- the model produces structured legal documents with its own internal deliberation.
	*	LitAssist Usage: o3-pro handles strategy-analysis, brainstorm-analysis, draft, counselnotes, and barbrief. These are all high-stakes legal generation tasks where the model's native reasoning outperforms prompt-directed CoT. Thinking effort is set to "high" or "max" depending on the command.

OpenAI GPT-5 Series (GPT-5, GPT-5.1, GPT-5 Pro)

The GPT-5 family represents OpenAI's unified system that can decide when to engage deeper reasoning or use tools. Unlike the O-series, GPT-5 models support system messages, but they share the restriction on sampling parameters:
	*	No Sampling Parameters: The entire GPT-5 series removed temperature and top_p to maintain reasoning quality. These parameters destabilise the internal reasoning process and are silently dropped if passed.
	*	Reasoning Effort Control: GPT-5.1 supports adaptive reasoning with effort levels none/low/medium/high. GPT-5 Pro has reasoning effort locked to "high" with no override. This is distinct from the O-series effort parameter -- GPT-5 models use a different internal routing mechanism.
	*	Verbosity Parameter: GPT-5 models support a separate verbosity control (low/medium/high) that governs response length independently of reasoning depth. LitAssist sets verbosity explicitly per command -- "high" for draft and barbrief (which need comprehensive output), "low" for lookup (which needs concise results).
	*	System Messages Supported: Unlike O-series, GPT-5 models accept system messages normally. LitAssist uses this for Australian law requirements, anti-injection, and anti-hallucination instructions.
	*	LitAssist Usage: gpt-5.1 handles standard verification and CoVe answer generation (where independent verification questions are answered by a different model than the one that generated the original document). gpt-5-pro handles heavy verification, soundness verification, and heavy CoVe answers -- tasks requiring maximum reasoning depth with the highest accuracy ceiling.

Anthropic Claude Series (Claude Sonnet 4.5, Opus 4.1, and Claude 4.6)

Anthropic's Claude models are trained with Constitutional AI principles and are known for strong instruction-following, long context windows (200K+ tokens), and thorough reasoning. The Claude 4.x family includes Claude Sonnet 4.5 (high-performance, efficient) and Claude Opus 4.1 (flagship reasoning and coding). Claude 4.6 / Opus 4.6 is the latest generation.
	*	Extended Thinking via Reasoning Effort: Claude supports extended thinking where the model produces a reasoning scratchpad before its final answer. Through OpenRouter, LitAssist controls this via the reasoning.effort parameter (mapped from thinking_effort in model_configs.yaml) rather than raw <thinking> tags. Effort levels range from low to max. For complex legal analysis (strategy generation, reasoning verification), higher thinking effort yields significant quality gains.
	*	High-Level vs. Step-by-Step Instructions: Anthropic's guidance notes that Claude often performs better with broad instructions to "think deeply" rather than overly prescriptive step lists. Start with general reasoning instructions and only fall back to granular step-by-step directives if the model struggles. Claude's own problem-solving strategy may exceed a human's prescribed steps.
	*	Using XML-Style Tags: Claude responds well to structured prompts using XML-style tags (<thinking>, <scratchpad>, etc.) for separating reasoning from answers. When providing few-shot examples, annotating reasoning in tags helps Claude recognise the desired output structure. This is particularly useful for extraction tasks where LitAssist needs both reasoning traces and structured outputs.
	*	Tools Disabled for Legal Generation: LitAssist sets disable_tools: true on all Claude configurations. This prevents the model from attempting tool calls during legal document generation, which would interrupt the output flow and add latency. Date injection is handled via a fallback mechanism that embeds the current date directly in the system prompt when tools are disabled.
	*	Large Context Strategies: Claude's 200K+ token context window is valuable for analysing lengthy case documents, statutory compilations, and multi-party proceedings. Structure large inputs with clear section headings or document markers (=== DOCUMENT ===). Place the specific question or instruction after the long content -- the model processes documents sequentially and focuses on the most recent instructions.
	*	Role and Tone Instructions: LitAssist defines Claude's role as a "senior solicitor with excellent knowledge of case and statute law" across strategy, brainstorm, and analysis commands. Claude follows role instructions literally, so craft them precisely -- overly restrictive stylistic constraints will be rigidly obeyed.
	*	Parameters: Claude supports temperature, top_p, top_k, and max_tokens. LitAssist uses temperature 0 for deterministic extraction (extractfacts), 0.2 for verification (where accuracy matters), and 0.7 for strategy generation (where some creative variation is beneficial).
	*	LitAssist Usage: Claude Sonnet 4.5 is the workhorse model handling extractfacts, strategy, brainstorm-orthodox, digest, caseplan, cove-questions, cove-verify, cove-final, and verification-light. Claude Opus 4.1 handles verify-soundness -- the most demanding verification task requiring maximum analytical depth.

Google Gemini 2.5 Pro

Google's Gemini 2.5 Pro features a 1 million token context window and a Mixture-of-Experts (MoE) architecture that dynamically routes parts of the prompt to specialised expert networks. It also supports multimodal input (images, audio, video), though LitAssist uses text-only capabilities.
	*	Massive Context for Legal Research: The 1M token window makes Gemini well-suited for research tasks that require ingesting large volumes of case law, statutory text, and secondary sources in a single prompt. LitAssist uses Gemini exclusively for the lookup command, where it processes research queries against comprehensive legal context.
	*	Low Temperature, Low Effort: LitAssist configures Gemini for lookup with temperature 0.2 and thinking_effort "low". The goal is fast, citation-focused retrieval rather than deep reasoning. Gemini's MoE architecture handles domain routing internally -- legal queries activate the relevant expert networks without explicit prompting.
	*	Formatting Consistency: Gemini can be verbose and may deviate from strict format requirements unless explicitly instructed. When precision matters, be very explicit: "Output only the requested format. No explanation or extra text." Double down on clarity and repeat format constraints if needed.
	*	Guiding Reasoning: Although Gemini is highly capable, it can produce overly descriptive or unfocused output without guidance. For legal research, constrain the response scope: "List only cases directly relevant to [issue] in [jurisdiction] from [date range]." Adding "be concise" or "focus on key holdings" improves output quality for research tasks.
	*	Parameters: Gemini supports temperature, top_p, top_k, and max_tokens. The standard sampling controls apply as with Claude. Set reasonable max_tokens limits -- Gemini can generate up to 64K tokens and will do so if unbounded.

xAI Grok Series (Grok-4)

Grok-4 is xAI's model used in LitAssist for creative, divergent legal strategy generation. It occupies a specific niche in the pipeline -- producing unorthodox strategies that push beyond established precedent.
	*	Creative Strategy Generation: LitAssist uses Grok-4 exclusively for the brainstorm-unorthodox command. The model is prompted to "provide creative, innovative legal strategies that push boundaries" while "acknowledging legal uncertainties and risks." The high temperature (0.8) and repetition_penalty (1.2) encourage novelty and discourage formulaic output.
	*	OpenRouter-Specific Parameters: Beyond standard sampling controls, Grok-4 supports min_p (0.05 in LitAssist config), top_a, and repetition_penalty through OpenRouter's extra_body mechanism. These parameters help shape the probability distribution for more diverse outputs.
	*	Paired with Analytical Models: Grok-4's creative output feeds directly into o3-pro's brainstorm-analysis step, where strategies are evaluated analytically. This pairing -- creative generation followed by rigorous assessment -- is a deliberate architectural choice. The prompting for each stage reflects this: Grok-4 receives open-ended creative instructions, while o3-pro receives structured analytical criteria.
	*	Role Definition: The system prompt for Grok-4 defines the role as "a senior solicitor with excellent knowledge of case and statute law" (consistent with other models) but adds instructions to "suggest novel approaches while maintaining ethical boundaries." This constrains creativity within professional bounds while still encouraging lateral thinking.

Reasoning Model Prompting: CoT Diminishing Returns

Recent research has significant implications for how LitAssist constructs prompts for its reasoning models:
	*	The Core Finding: The Wharton research report "To Think or Not to Think" (Swaroop et al. 2025) demonstrated that chain-of-thought prompting provides minimal benefit for reasoning models. On o3-mini and o4-mini, CoT improved performance by only 2.9-3.1%, compared with 25-39% improvement on non-reasoning models like GPT-4o-mini. The internal reasoning process of these models already performs CoT-equivalent deliberation.
	*	OpenAI's Official Guidance (February 2025): For reasoning models, OpenAI recommends: (1) keep prompts simple and direct, (2) avoid chain-of-thought instructions like "think step by step," (3) avoid few-shot examples (they can actually degrade performance), (4) use delimiters like XML tags or triple quotes to clearly separate context from instructions.
	*	LitAssist's Approach: Rather than embedding CoT instructions in prompts, LitAssist controls reasoning depth through the thinking_effort parameter. This is mapped to each provider's native reasoning control (OpenRouter's reasoning.effort object). The prompt itself focuses on task definition, constraints, and output format -- not reasoning methodology.
	*	When CoT Remains Valuable: For standard models (Claude Sonnet 4.5, Gemini 2.5 Pro), explicit reasoning instructions still improve output quality. LitAssist uses CoT-style prompting for Claude on extraction (extractfacts), digestion, and case planning tasks, where the model benefits from structured reasoning traces in the output (Issue/Applicable Law/Application/Conclusion/Confidence/Sources format).
	*	Reserve Reasoning Models for Complex Tasks: OpenAI's guidance recommends reserving reasoning models for tasks requiring 5+ reasoning steps. Simpler tasks run faster and cheaper on standard models. LitAssist follows this principle -- o3-pro handles only the most analytically demanding commands (strategy analysis, document drafting, bar briefs), while Claude Sonnet 4.5 handles the bulk of generation work.

Structured Output and Format Enforcement

Consistent, parseable output is critical for LitAssist's multi-stage pipeline where one model's output feeds into another model's input:
	*	YAML vs JSON for Structured Output: Research on structured output formats shows YAML achieves 76% accuracy, JSON 74%, and Hybrid CSV/Prefix 82% in structured output tasks. YAML's advantage lies in readability and the ability to embed comments (using #) as reasoning anchors before critical fields. LitAssist stores all prompt templates in YAML and requests structured output in formats designed for reliable parsing.
	*	Document Separation Markers (Prompt Scaffolding): LitAssist uses a consistent === NAME === marker convention to delineate content boundaries in prompts. Examples: === DOCUMENT ===, === CONTEXT ===, === QUESTIONS ===, === STRATEGIES CONTENT ===. This serves two purposes: (1) the model understands where different content sections begin and end, and (2) the anti-injection guard explicitly instructs the model to treat content within markers as data to analyse, not instructions to follow.
	*	Output Format Specification: Always specify the exact output format expected. For legal documents, LitAssist requests markdown headers and numbered paragraphs. For reasoning traces, the format is explicitly defined: Issue, Applicable Law, Application to Facts, Conclusion, Confidence (0-100%), and Sources. Providing a concrete example of the expected format in the prompt dramatically improves compliance.
	*	Validation as External Data: Treat all model output as external, untrusted data. Validate format with code before passing to downstream stages. LitAssist uses regex-based extraction for reasoning traces and section parsing for document outputs. If output is malformed, the pipeline raises an error rather than attempting to guess the intended structure.

Anti-Hallucination Techniques for Legal AI

Factual accuracy is non-negotiable in legal work. LitAssist implements multiple anti-hallucination layers:
	*	Explicit Placeholder System: The base anti-hallucination prompt (injected into every LLM call) instructs models to use placeholders for uncertain information: [NAME TO BE PROVIDED], [DATE TO BE CONFIRMED], [CITATION TO BE VERIFIED], [AMOUNT TO BE CONFIRMED]. Placeholders are always preferable to invented specifics. The draft pipeline includes a downstream check for likely hallucinations.
	*	"According to..." Prompting: Directing the model to ground responses in specific sources discourages invention. For legal research and citation tasks, prompts should reference specific source material: "Based on the documents provided above..." or "According to the case law in the === CONTEXT === section..." This guides the model toward fact-based reasoning from supplied sources rather than training data recall.
	*	Brevity Reduces Drift: Shorter, more focused prompts and response constraints reduce hallucination risk. Research indicates that longer, more open-ended responses allow the model to drift into confabulation. LitAssist's verification prompts are deliberately concise and constrained in scope.
	*	Chain-of-Verification (CoVe): LitAssist implements a 4-stage CoVe pipeline: (1) generate verification questions about the document, (2) answer questions independently using a different model (gpt-5.1, not the model that generated the document), (3) detect inconsistencies between answers and the original document, (4) regenerate corrected content. Using a different model for the answer stage (cross-model verification) increases the likelihood of catching errors.
	*	Self-RAG Concept: Self-Reflective Retrieval-Augmented Generation dynamically decides when and how to retrieve additional information, evaluates relevance of retrieved data, and critiques its own outputs. This pattern is applicable to LitAssist's lookup system, where query augmentation before retrieval could bridge the gap between vague user queries and specific retrievable legal terms.
	*	Confidence Levels: All reasoning traces include explicit confidence scores (0-100%) with supporting sources. This provides downstream consumers (and human reviewers) with calibrated uncertainty signals rather than presenting all conclusions with equal weight.

Legal Domain Prompting

Prompting for legal AI requires domain-specific techniques beyond general LLM best practices:
	*	Embed Jurisdiction Context: Never rely on the model's generic legal knowledge. LitAssist's base system prompt (base.yaml: australian_law) specifies: Australian law only, Australian English spelling, explicit jurisdiction identification (Commonwealth, State, or Territory), and prohibition of US legal terminology. This base prompt is injected into every LLM call.
	*	Structured Legal Analysis Framework: LitAssist's reasoning traces follow the IRAC-derived format: Issue, Applicable Law, Application to Facts, Conclusion, Confidence, Sources. This framework is enforced via the reasoning.yaml prompt template, which instructs the model to structure its reasoning in this format. The explicit framework reduces omissions and ensures each legal conclusion is grounded in identified law and fact.
	*	Citation Format Enforcement: Prompts specify medium neutral citation format (Case Name [Year] COURT_ID Number) with pinpoint references using paragraph numbers, not pages. The instruction "Only cite cases you can verify or have high confidence exist" combined with the placeholder "[CITATION TO BE VERIFIED]" creates a pressure valve -- the model can indicate a relevant authority exists without fabricating a citation.
	*	Anti-Injection for Legal Documents: User-provided case documents and evidence may contain instruction-like text (e.g., contractual clauses saying "do not include..." or "ignore..."). LitAssist's anti-injection prompt (base.yaml: anti_injection) explicitly instructs the model to treat all content within document markers as data to analyse, not instructions to follow. This prevents adversarial or accidental prompt injection through case materials.
	*	Specificity Over Generality: Effective legal prompts include jurisdiction, date ranges, and specific statutory references. Weak: "Summarise the law on negligence." Strong: "Analyse the elements required to establish negligence in New South Wales, with reference to Civil Liability Act 2002 (NSW) and relevant High Court authority from 2015 onwards." The more specific the prompt, the less room for the model to fill gaps with generic or incorrect information.

Conclusion

Prompt engineering for LitAssist requires model-family awareness because each model in the pipeline has distinct capabilities and constraints:
	*	OpenAI O-Series (o3-pro): No system messages, no sampling parameters, no CoT instructions needed. Keep prompts simple and direct; control reasoning depth via thinking_effort. Used for the highest-stakes analytical and drafting tasks.
	*	OpenAI GPT-5 Series (gpt-5.1, gpt-5-pro): No sampling parameters but supports system messages. Adaptive reasoning with effort levels. Used for verification where cross-model checking catches errors the generating model missed.
	*	Anthropic Claude (Sonnet 4.5, Opus 4.1): Full sampling support, excellent instruction-following, 200K+ context. Benefits from explicit CoT prompting and structured reasoning frameworks. The workhorse model for most generation and verification tasks.
	*	Google Gemini (2.5 Pro): 1M context, MoE architecture. Used for research/lookup with low temperature and low thinking effort. Constrain output format explicitly to avoid verbosity.
	*	xAI Grok (Grok-4): Creative divergent generation with high temperature and repetition penalty. Used exclusively for unorthodox strategy brainstorming, paired with analytical models for evaluation.

Cross-cutting techniques applicable to all models in the pipeline:
	*	Prompt scaffolding with === markers for content boundaries and anti-injection protection.
	*	Explicit output format specification with examples for every structured output task.
	*	Anti-hallucination placeholders rather than allowing invented specifics.
	*	Chain-of-Verification using cross-model checking for critical legal outputs.
	*	Jurisdiction and domain context embedded in base prompts rather than relying on model training data.
	*	Reasoning depth controlled via parameter (thinking_effort) rather than prompt instructions, except for standard models where CoT prompting remains effective.
